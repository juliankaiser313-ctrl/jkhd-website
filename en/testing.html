// Testing

How we test our own system.

We build quantitative systems and run them ourselves. This page says how we test them, what our own tests have taught us — and what we would recommend to anyone setting out to do the same.

// How we test

Five stages before a program may touch money.

Every stage is allowed to stop the process. Stopping is not the setback, it is the point of the exercise — the earlier, the cheaper.

01

Red first

A test only counts here once it has been red with the fault present: first the test, then the repair. Every item on our task list has its own field for that — leaving it empty means nothing was proven, only claimed.

02

A frozen comparison run

A stored run is replayed line by line: two runs with the same input must be bit-identical. A second test deliberately gives a different input and demands a different result — otherwise the first would pass even if the run ignored the input entirely. If the comparison file is missing, the test fails; it is not skipped.

03

Searching against chance

The search runs on the earlier part of the history and is confirmed on the later one; any record whose measurement window reaches into the confirmation part is dropped beforehand, and in a rolling procedure the selection has to hold again at every time boundary. Costs and slippage sit inside the figure a candidate is judged by. The same search additionally runs over series in which the link between signal and future has been destroyed, and over one with an effect built in on purpose: that tells us how often it fires on noise, and whether it finds anything at all.

04

Shadow operation under the locks that matter

A candidate first runs along without money. While it does, the locks that decide about the signal must apply to it as well: regime filter, repetition stop, only one open position. The capital limits fall away because no capital is at stake — everything else does not. If a single one were missing, entries would appear that never could have happened with money at stake, and their results would land in the same evidence that later decides on promotion.

05

Monitored continuous operation

A process being listed by the operating system does not prove it is working. So the clock writes its own sign of life out of wall time and a counter; a watchdog ends a stalled run and restarts it only on the next pass, rather than letting two run at once.

Two things that belong with this: warnings count as errors here, and every exception to that is listed individually with its reason. And the one run that carries the whole chain into the execution path takes minutes rather than seconds — it is excluded from the normal test run and tied to a fixed occasion instead: before any change to the clock it is mandatory. That this leaves a gap in day-to-day runs is itself asserted in the test suite, so the gap stays named instead of going quiet.

// Stress tests

What we break on purpose.

A system shows its character not in normal operation but on the day something fails. So we bring that day forward — and write down what has to come out of it.

Connection lost mid-order

The broker loses the connection while an order is in flight, and never answers.

Expected No trade booked, the slot stays taken, nothing is sent after it

Restart in mid-session

The process dies between two day boundaries while the book is open.

Expected Balance and daily loss survive — and the daily loss limit can only get stricter, never more generous

Two writers, one file

Both have read, neither has written; then both write — inside the same process. Two separate processes are not covered by our code; that gap is named.

Expected No entry lost, the file's checksum chain intact

Half a final line

The process is killed hard and the last log line breaks off mid-word.

Expected Writing can continue, and the truncated bytes are kept as evidence

Process runs, work stalls

The process sits there perfectly, but no longer processes a single tick.

Expected End it first, restart it on the next pass

Switching between practice and earnest

The mode switch is requested while the position state is unclear.

Expected Open, contradictory or unreadable positions block the switch

// Learned

Six lessons from our own tests.

Not from books, but from tests that were wrong themselves. Each of them lulled us into safety for a while.

01

Green with nothing behind it

Our own check for coding rules silently fell back to a plain syntax test whenever the tool was missing, and passed that success on. For six weeks it reported green without having checked a single rule.

The lesson

A green result with nothing behind it is worse than a red one: it answers the question without asking it. Today the command refuses the green result and says that nothing was checked.

02

The test was the culprit

A full test run wrote into the control file of the running system and thereby set the kill switch. A second time it created files inside the data of the running programs — and that was noticed only by chance.

The lesson

The separation between testing and operation has to be enforced, not agreed upon. And afterwards you go and look at what has newly appeared in the real data.

03

The net without meshes

One of our frozen comparison runs was cited throughout our own task list as the safety net for position size, daily budget and order path. Measured, that very run does not execute a single trade — the trading sits in a different run, and that was written down nowhere.

The lesson

What a test run actually touches has to be measured. Nothing follows from the name of a test — and an unnamed gap turns into a silent assumption.

04

Tests that cannot go red

Our own suite contained assertions made always true by an appended expression: in the report they counted as checks and checked nothing. When we armed them again, two held straight away — the third was simply worded wrongly.

The lesson

Whoever switches a disabled check back on finds the fault in the check at least as often as in the code under test. Without switching it on, neither ever comes to light.

05

Green one day, red the next

Our deepest run read the control layer of the running system. It came out green or red depending on what had last been clicked on the panel — without a single line of code having changed.

The lesson

A test whose result depends on anything other than the code under test is worthless as a net. Worse: it trains you to click red runs away.

06

The floor is not a data problem

How small an effect may be for us to detect it at all has a fixed base made of trading costs and a safety haircut. No additional amount of data buys that away; only the part above it improves.

The lesson

Before obtaining more data, measure which part of your own blindness actually depends on the amount of data. The rest is the physics of costs.

// Recommendation

What we would test — in this order.

No prescription, just the order that would have saved us work. Starting at the top means having to believe less further down.

Step 01

The measuring device first

Before you test your system, test your test. Otherwise you are measuring your confidence, not your system.

  • Two runs with the same input must give the same result — before that you are comparing chance
  • Run every check once against the fault it is meant to find
  • One single command that reads the running state and delivers a verdict at the end — a checklist in a document ends up merely being copied out
  • Measure which paths a test run touches, and name the gap explicitly
  • Build guards on the property, not on a list of known names: our first one counted three known shapes and missed five more of the same kind
Step 02

Data and features

Our most expensive faults were sitting here — and at first glance they were invisible.

  • For every feature, the question: was this value complete at the moment of the decision?
  • A range computed across the night measures the overnight gap, not a tradable path — session boundaries belong in the calculation
  • Contract rolls and clock changes: walk them through on the data, do not assume them
  • A half-written log must stay readable and keep the remainder as evidence
Step 03

Statistics

What is being tested here is not the best result, but the search that led to it.

  • Search and confirm on separate stretches; lock the border zone between them
  • Costs and slippage inside the figure you test against — not as a deduction afterwards
  • And the part of the costs that grows with the distance to the stop calculated separately from the fixed part
  • Run the same procedure over data with no link in it and count how often it reports something
  • Alongside that, a series with an effect built in: does the setup find anything at all?
  • In a rolling procedure the selection has to hold again at every time boundary
  • Note down for every procedure what it cannot see — in the same place as the procedure itself
Step 04

Risk

A good average says nothing about whether one sequence of results tears the account along the way.

  • Draw many possible sequences of results and count how often the account fails
  • For every unavoidable assumption, pick the variant whose error makes the result look worse
  • Know your own cost floor before buying more data
  • Demand a real distance from zero at your own gate, and do not ask the question again after every new result — otherwise it eventually lets anything through
Step 05

Execution and operation

The part backtests know nothing about — and the part where money actually moves. The failures from the section above belong here; and these four as well:

  • Let a candidate run along without money first — under the same locks that decide about the signal — and check that this recording does not stop the moment it is promoted
  • Reconcile your own positions against the broker's: a position that exists on only one side has to produce a line in the log
  • Check that a rule is really called in operation — we had a finished invariant against phantom positions sitting there, and the only thing calling it was a test
  • A failed run must never look like a null result — otherwise every crash improves the verdict
How to tell that a test is worth nothing: it cannot go red. Or it was skipped — and in a short report a skip looks almost like a pass. Or its result depends on something other than the code under test. Or its failure message promises more than it really checks: that message is an assurance to everyone who reads it later.

// Limit

What these tests do not achieve.

None of them creates an advantage in the market. They prevent self-deception: taking noise for a pattern, a number for a measurement, a green tick for proof. Part of it is also precaution — there is no real broker attached to our system yet, and the failure drills run against stand-ins. And what is not tested sits in the same list as what is: two writers in two processes, for one. Or the single command that reads the running state and delivers a verdict — we recommend it above, and we do not have it yet.
